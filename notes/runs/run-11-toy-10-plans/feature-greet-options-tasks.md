# Introduction

![Status: In progress](https://img.shields.io/badge/status-In%20progress-yellow)

These tasks implement `plans/greet-options/feature-greet-options-spec.md` (v0.4) with test-driven development. Every task follows **Red → Green → Refactor**:

1. **Red:** write the next listed test and confirm it fails for the right reason: an assertion about behaviour, not an import error or a missing mock.
2. **Green:** write the minimum code that makes it pass. Repeat 1-2 for each listed test.
3. **Refactor:** with the tests green, clean up, then run the lint and type checks.

A test listed under **Guard:** is expected to pass as soon as it is written, because earlier code already gives the behaviour. It is not logged as a difference.

Rules:
- Tests never call the network and never write a file. The only boundary crossed is the filesystem, and it is crossed for real: config tests point `cwd` at a committed fixture directory under `test/fixtures/`.
- Tests drive the two seams agreed in spec §9: the unit seam (`parseOptions`, `loadConfig`, `mergeOptions`, `buildGreeting`, `renderOutput`, `formatUsage` called directly) and the process seam (`node bin/greet.js` as a child process). Nothing is mocked.
- The existing test helper `run` keeps its signature. A second helper `runIn(cwd, ...args)` is added next to it for the fixture-directory runs.
- Tasks marked **Manual** need a real human. Record what was observed in the task and, where it changes the plan, under Differences.
- Tick a task (`[x]` plus the ISO date in Done) when its tests pass. Tasks run in order within a unit.
- The **Spec** column maps each task to the spec's ids. The **Files** column lists every file the task touches.

## Decisions taken for these tasks

Settled up front so work can start. Revisit in the last task if any turns out wrong.

| Decision | Taken |
|---|---|
| Where the option list lives | One constant in `src/greet.js`, `OPTION_SPECS`, holding the five flags with their kind (boolean or value) and their allowed values. `parseOptions` reads it, so adding a flag is one entry (RISK-004, GUD-001). |
| Shape of a usage error | `UsageError` is an `Error` subclass with a `reason` property (a short lowercase string, no trailing newline). `parseOptions` and `loadConfig` throw it; `bin/greet.js` catches it. `formatUsage(reason)` builds the single stderr line (GUD-004, GUD-005). |
| How `--times` is validated | A plain digit string: the value must match `/^[1-9][0-9]*$/` and then be an integer from 1 to 5. `03` and `+2` are rejected because of the digit-string rule, not because of the range (REQ-032, Q-1). |
| What type the count carries | The resolved option record holds `times` as an integer (spec §3), and the config path gives a JSON number (REQ-068), so `parseOptions` converts the validated digit string to a number at the parse boundary. One type per key in the merged record (REQ-002). |
| How a flag value that starts with `-` is handled | The parser never consumes an argument that starts with `-` as a value, so `--name -x` and `--name --shout` are both `missing value for --name` (REQ-074, Q-2). |
| Where the config fixture directories live | `test/fixtures/<case>/greet.config.json`, one directory per case, named after the case (`no-config`, `empty-config`, `unknown-key`, `invalid-json`, `top-level-array`, `top-level-null`, `bad-lang`, `bad-shout`, `bad-format`, `good-format`, `name-number`, `name-empty`, `times-zero`, `times-string`, `times-fraction`, `times-six`, `name-ada-lang-es`, `parent-has-config`). The directory with no config file holds a `.gitkeep` so git keeps it. Names are the implementer's choice, but the fixtures are committed, never generated at run time (spec §8, RISK-002). |
| How `loadConfig` is called in a test | `loadConfig(cwd)` takes the directory path as an argument, so a test points it at a fixture directory rather than the real working directory (PAT-001). |
| Where the name is upper-cased | The fully assembled line is upper-cased after the word, the comma, the space and the name are joined, so the comma and the name are upper-cased too (REQ-020, REQ-021, D-01). |
| How the JSON value is built | `JSON.stringify({ greeting: value })` on an object with exactly one key, so the printed form has no space after the colon. The repeated value is the lines joined by `\n` with no trailing newline inside the string (REQ-051, REQ-053, REQ-055, RISK-003). |
| How the CLI exits | The script sets `process.exitCode` and falls off the end. `process.exit` is not called, because `process.stdout` is asynchronous when it is a pipe and an exit right after a write can truncate the output (spec §4.2). |
| How a config key that is not one of the five is treated | It is ignored and never validated, so a forward-compatible config file does not break (REQ-061, D-15). |
| What an invalid config value's reason says | `invalid value for <key>: <value>` for a config key, with the key name without the `--` prefix, and `empty value for name` for the empty config `name`. A flag reason names the flag with its `--` prefix (spec §4.3, Q-6). |
| Whether `greet.config.json` is added to `.gitignore` | No. The file is never written by the CLI and never created by the tests, so there is nothing to ignore; whether a project commits one is the project's choice (spec §3). |

## Review focus

The inputs and failure modes most likely to hurt a real user that no requirement spells out, most likely first. Each one has a test in the named task.

1. A flag value that looks like another flag (`greet --name --shout`) is swallowed as a name by a careless parser, and the user gets `Hello, --shout` instead of a usage error. Test in TASK-202.
2. A config file that is present but broken (`null` at the top level, or `{"times": "3"}`) makes the CLI crash with a `TypeError` stack trace instead of a usage line, because `typeof null === 'object'`. Test in TASK-301.
3. A config value that is invalid but is overridden by a flag is silently accepted when the merge runs before the validation, so the file is never checked. Test in TASK-302 and TASK-602.
4. The output is truncated when the process exits before the stdout stream flushes, which happens whenever the output is piped (`greet --times 3 | cat`). Test in TASK-401.
5. A name with a shell metacharacter (`--name "Bob; rm -rf /"`) is passed to a shell and the command runs. Test in TASK-702.
6. The JSON output is written with a space after the colon (`{"greeting": "Hello, world"}`), so a consumer that compares bytes against the pinned compact form fails. Test in TASK-204 and TASK-402.
